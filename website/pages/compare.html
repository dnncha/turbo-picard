Why stay Picard-compatible when replacing Java?

Rewriting downstream parsers, WDL/Nextflow modules, and QC thresholds to adopt an unrelated CLI creates validation risk across every consumer in a pipeline. Turbo Picard keeps the exact command name, arguments, flags, metrics tables, and sidecars of Picard so you can accelerate one slow step at a time while checking byte-level or semantic equivalence directly against Picard.

Configured upstream fallback handles unsupported commands and edge options safely, while TURBO_PICARD_REQUIRE_NATIVE=1 lets you guarantee no silent Java fallback during native benchmarking or production execution.

When a specialist still wins

  • GTF/GFF3 RNA-seq models or BigWig tracks: Turbo Picard runs refFlat CollectRnaSeqMetrics and CollectSamErrorMetrics natively with Picard-identical TSV outputs, while Riker includes native GTF/GFF3 transcript annotation and BigWig per-base depth tracks.
  • Pre-sort aligner pipes: If you are designing a brand-new alignment pipeline and do not need Picard compatibility or post-sort optical families, SAMBLASTER or dupblaster in the aligner stream avoids an extra pass.
  • Native samtools chains: If your workflow already runs samtools fixmate -m before sorting, samtools markdup avoids adding a separate command layer—just validate downstream tag expectations.

Rules for fair benchmarking

Compare the same biological input, reference FASTA, thread count, compression level, and required output files. For samtools markdup and dupblaster, include any required name-grouping, fixmate, and coordinate-sort stages when starting from coordinate-sorted BAMs. Report wall time, peak RSS, temporary disk usage, and output parity together.
