Sorting performance depends on the requested order, the records held in memory and the temporary storage doing the merging. A faster comparison loop is only one part of the job.

Coordinate and queryname order solve different problems.

Coordinate sorting groups alignments by reference location and supports coordinate-based access and BAM indexing. Queryname sorting puts read names together for workflows that need related records adjacent. A coordinate-sorted file is not a substitute for a queryname-sorted one simply because both are called “sorted.”

Turbo Picard’s SortSam implements those two orders for SAM, BAM and CRAM within its documented scope. CRAM paths require an explicit reference. Other sort orders and advanced options should stay with upstream Picard.

Check the consumer first. Sorting a file to the wrong order, then sorting it back in the next task, is avoidable work regardless of which tool does it. Do not change the sort-order header as a replacement for ordering the records.

Treat the memory buffer and scratch disk as a pair.

An external sorter writes sorted runs when its in-memory buffer fills, then merges those runs. A smaller MAX_RECORDS_IN_RAM reduces a buffer but can create more runs and more temporary I/O. A much larger buffer may push the task against its memory limit. Choose it with both constraints in mind.

Use TMP_DIR to select storage that has enough capacity, quota and throughput for the job. Avoid assuming a shared network directory will behave like local scratch. Keep the input, final output and temporary space in your resource accounting.

Version {{VERSION}} replaces a scan across active BAM sort runs with heap-based selection. That reduces the selection comparisons from linear to logarithmic in the number of runs, while retaining the comparator and tie ordering. It is an implementation improvement—not a measured promise of a particular end-to-end speedup.

An explicit coordinate-sorting trial.

Start from an isolated installation. This example requests a fresh output, a BAM index and a checksum, with a separate temporary directory.

Shell example
run_dir="$(mktemp -d)"
mkdir "$run_dir/scratch"
TURBO_PICARD_REQUIRE_NATIVE=1 \
  "$HOME/.venvs/turbo-picard/bin/turbo-picard" SortSam \
  I=/data/unsorted.bam O="$run_dir/coordinate.bam" \
  SORT_ORDER=coordinate TMP_DIR="$run_dir/scratch" \
  MAX_RECORDS_IN_RAM=100000 CREATE_INDEX=true CREATE_MD5_FILE=true
printf 'Sorted outputs retained in %s\n' "$run_dir"

For queryname sorting, use SORT_ORDER=queryname and do not request a coordinate BAM index. The sample buffer size is a starting configuration, not a total-process RAM cap.

Equal keys still need a stable contract.

Two valid coordinate-sorted BAMs need not be byte-identical. Compression, program headers and some record-order details may differ. Decide which differences are allowed in your workflow; never remove scientific fields from a comparison just to make it pass.

The sorter’s regression tests cover stable cross-run ties, spill cleanup and truncated temporary-record detection. Those tests do not replace evaluating your actual data and downstream consumer. Check the required sort order, the set of records, header references and requested sidecars.

A comparison with samtools sort should match the requested ordering semantics, thread/resource allocation and output requirements. Queryname ordering conventions and optional behaviours need particular attention. There is no useful universal winner independent of the task.
