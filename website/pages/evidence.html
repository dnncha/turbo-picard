Measured trade-offs and parity notes: On 30x MarkDuplicates, Turbo Picard used 4.3× more scratch disk than Picard (99.2 GB vs 23.3 GB; tracked in #86 ↗). Build 9a15db96 differed on optical duplicate counts because Picard stores tile coordinates as 16-bit signed integers and splits mixed-orientation sets before optical detection; PR #87 fixed both, yielding identical metrics and identical MD5 across SAM columns 1–11 for all 79,289,617 duplicate-flagged reads. PR #88 added @PG tag chaining, verified on chr21 (11.4M records); the full 30x BAM awaits a rerun on the #88 build.

Direct CRAM reading: Picard 3.5.0 fails to open the original 1000G CRAM with its .crai index (CRAMException). Turbo Picard reads it directly: on Host A, CollectWgsMetrics finished in 4 m 53 s at 689 MB RSS and MarkDuplicates in 41 m 44 s at 1.06 GB RSS. The tables above use the BAM conversion so Picard could run.

What parity covers and where it stops

The synthetic suite checks selected commands, options, and fixtures. Pinned public real-data evidence covers a 12-command release set on documented small inputs (mitochondrial BAM/CRAM and SNVQ fixtures). Neither replaces validation on your own sequencing data.

Check the comparison contract for each command before switching. Metrics text is the parity target for supported collectors; lightweight PDF summaries do not reproduce Picard’s R charts. Compressed-file bytes and @PG program headers require explicit comparison rules rather than a blanket byte-identical claim.

Saved benchmark exceptions

AccelerationStatus, capabilities, doctor, explain, mcp, and trial are utility or inspection commands, not timed upstream replacements. CollectHsMetrics has separate parity checks and measured 12.8x faster than Picard 3.4.0 on capture-panel intervals in PR #76. CollectRnaSeqMetrics and CollectSamErrorMetrics also have dedicated Picard parity gates, while suite-integrated benchmarks await representative capture, transcript, and error fixtures in CI.

Turbo Picard is not a full Picard suite. Unsupported commands and options require upstream Picard when fallback is configured. Switch only the commands where the evidence supports the change.

Pinned public inputs

A scientific release requires a pinned comparison portfolio beyond one tiny fixture, though these inputs are still not proof for every dataset. The current 12-command release set runs against designated release_candidate inputs alongside lighter public_smoke checks. Record the full 40-character Git commit SHA and the input SHA-256 when citing or reproducing a case.

Reproduce checks and cite releases

Four repository checks tie public claims on this site to saved logs, command coverage, and release evidence:

Evidence verification · repository checkout
python3 tools/verify_benchmark_log_evidence.py
python3 tools/verify_benchmark_suite_coverage.py
python3 tools/verify_benchmark_thresholds.py
python3 tools/verify_real_data_evidence.py --release-ready

The fixture-suite release thresholds are 5.00x floor, 20.00x geometric mean, and 50.00x maximum. These are internal saved-suite gates, not promised speedups for other inputs.

For the software citation, consult CITATION.cff ↗ and cite the archived turbo-picard release you used. Cite benchmark inputs separately, preserving the accession or source revision and input SHA-256. Never attach an older archival DOI to a newer release.
