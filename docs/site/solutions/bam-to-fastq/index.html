02 / Read export

BAM to FASTQ, without the guesswork

Paired FASTQ output depends on read pairing, orientation and filtering—not just changing a file extension. Make those choices explicit and avoid holding distant mates in memory.

Coordinate order separates mates. Export has to reunite them.

A coordinate-sorted BAM is organised for reference access, not for writing paired FASTQ records next to each other. Mates can be far apart. An exporter that waits for each mate in memory can become expensive on large or awkward inputs.

Turbo Picard’s native SamToFastq supports paired, single-end, dedicated unpaired, interleaved and compressed outputs in its documented scope. For BAM or CRAM not declared queryname-sorted, setting TMP_DIR or MAX_RECORDS_IN_RAM enables a bounded temporary queryname stage. That trades scratch I/O for controlled sorting buffers.

Do not edit the BAM header to claim queryname order when the records are not actually ordered that way. Check how the input was produced and validate it when necessary. For CRAM, supply the exact reference explicitly.

A paired-export example with explicit temporary storage.

This is an example for a BAM containing complete primary read pairs. It requests native execution, gzip outputs and a fresh scratch directory. Existing input and output files are not reused.

Shell example
run_dir="$(mktemp -d)"
mkdir "$run_dir/scratch"
TURBO_PICARD_REQUIRE_NATIVE=1 \
  "$HOME/.venvs/turbo-picard/bin/turbo-picard" SamToFastq \
  I=/data/coordinate-sorted.bam \
  F="$run_dir/reads_R1.fastq.gz" \
  F2="$run_dir/reads_R2.fastq.gz" \
  TMP_DIR="$run_dir/scratch" MAX_RECORDS_IN_RAM=100000
printf 'FASTQs retained in %s\n' "$run_dir"

A buffer of 100,000 records is an example configuration, not a promise of a fixed memory footprint. Allow enough scratch capacity for sorting and output files. For an explicit unpaired output, review UNPAIRED_FASTQ and the pairing requirements; do not assume that output is a repair mechanism for malformed or missing mates.

Check more than the number of lines.

Orientation and original read sequence

Aligners represent reads relative to the reference. Picard-style RE_REVERSE handling matters when returning reads to sequencing orientation. Clipping, hard-clipped bases and optional original-quality tags can also affect what is recoverable. A FASTQ export cannot conjure information that is absent from the alignment file.

Which records belong in the export

Primary, secondary, supplementary and vendor-quality-filtered records are not interchangeable. Carry over the exact intended filtering options rather than comparing two tools’ defaults and assuming they mean the same thing.

Pairing and downstream consumption

For complete paired outputs, check record counts, mate identifiers and paired order. Compare sequences and quality strings—not gzip bytes, which need not be identical for the same reads. Run the downstream consumer on the candidate outputs. A successful exit code alone is insufficient.

When this is a good fit.

Start here when your workflow already uses Picard’s export interface and you need explicit, tested behaviour for paired or per-read-group output. Keeping F, F2, OUTPUT_PER_RG and your read filters can be less disruptive than rewriting a task around a different CLI.

samtools fastq may be an excellent choice in a samtools-oriented pipeline. It has its own ordering and filtering contract. Compare equivalent outputs after the required input preparation rather than declaring one exporter a universal winner. Unsupported Turbo Picard export combinations should stay with upstream Picard.
