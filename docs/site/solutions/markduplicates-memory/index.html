MarkDuplicates: slow runs and memory failures

Eliminate Java heap overhead and OOM kills with a bounded two-pass native planner—up to 5x–19x faster and 11x–18x less RAM than Picard, and 4x less RAM than FastDup with exact Picard output parity.

Measured speed and memory vs Picard, FastDup, and samtools.

On Linux x86_64 with 1 pinned CPU and BAM compression level 5 (competitor suite ↗):

  • paired-600k (600k pairs): Turbo Picard finished in 1.054 s / 94.1 MiB (full_parity: true), compared to Picard 3.4.0 (5.423 s / 1,052.6 MiB — 5.15x slower, 11.2x more RAM), FastDup (1.131 s / 383.8 MiB — differs from Picard, 4.1x more RAM), and the samtools markdup pipeline (1.982 s / 235.7 MiB — differs from Picard).
  • gatk-na12878-mito (real NA12878 chrM): Turbo Picard finished in 0.141 s / 9.5 MiB vs FastDup (0.201 s / 356.7 MiB) and Picard 3.4.0 (2.678 s / 721.3 MiB — 19.0x faster, 75.9x less RAM).
  • PR #76 core overhaul (Apple M5, 1.2M paired reads): Turbo Picard dropped to 0.303 s / 73.8 MiB vs Picard 3.4.0 (2.747 s / 1,331.2 MiB — 9.06x faster, 18x less RAM), a 2.07x speedup and 37% RAM cut even against prior main.

Start with the failure, not a larger heap flag.

A Java OutOfMemoryError, a scheduler OOM kill, and a scratch-disk error are different failures. -Xmx caps only the JVM heap, not native compression buffers or total RSS—raising -Xmx to your cgroup limit often triggers kernel OOM kills instead of solving the bottleneck.

What you observeWhat to inspect
Java heap errorJVM flags, scheduler memory limit, and sorting-buffer settings.
Scheduler OOM killPeak RSS and cgroup limits, not just -Xmx.
Long quiet periodsTemporary-file growth, scratch disk throughput, and BGZF compression threads.
No space leftScratch capacity, quota, and inode limits under TMP_DIR.

How Turbo Picard keeps memory bounded.

Native MarkDuplicates removes the JVM and processes eligible coordinate-sorted inputs—a single BAM, a single CRAM with an explicit reference, or globally coordinate-ordered multiple inputs—using a two-pass external planner that replays the alignment stream for output instead of holding all reads in RAM.

Lazy mate caches, template-level compact pair records, bloom-filtered fragment dominance checks, and pooled external sort buffers keep resident memory flat as input depth grows, while preserving Picard tie-breaking, barcode tags, optical duplicate detection (or READ_NAME_REGEX=null), duplicate-set tags (DS/DI), and metrics histograms.

Try a native run in isolation.

Run explicitly with TURBO_PICARD_REQUIRE_NATIVE=1 and dedicated scratch storage:

Shell example
run_dir="$(mktemp -d)"
mkdir "$run_dir/scratch"
TURBO_PICARD_REQUIRE_NATIVE=1 \
  turbo-picard MarkDuplicates \
  I=/data/sample.bam \
  O="$run_dir/marked.bam" M="$run_dir/duplicate_metrics.txt" \
  TMP_DIR="$run_dir/scratch" MAX_RECORDS_IN_RAM=100000
printf 'Results retained in %s\n' "$run_dir"

For CRAM inputs, pass REFERENCE_SEQUENCE=/data/reference.fa. Control worker threads independently with TURBO_PICARD_READER_THREADS, TURBO_PICARD_WRITER_THREADS, and TURBO_PICARD_INDEX_THREADS.

Keep exact Picard semantics.

Compare duplicate flags, representative selection, optical decisions, barcode grouping, and metrics directly on a representative BAM or CRAM via the comparison builder. Note that setting READ_NAME_REGEX=null disables optical detection and changes metrics—never compare runs with mismatched optical settings.

When to keep Picard: an unsupported option, unsorted multi-file streams that cannot take the bounded coordinate plan, or a representative comparison that fails. Native-only mode fails fast rather than silently falling back to Java.
