01 / Duplicate marking

MarkDuplicates: slow runs and memory failures

A killed job is not a diagnosis. Find out whether the limit is Java heap, total process memory or scratch I/O—then decide whether a native path is the right fix.

Start with the failure, not a larger memory request.

A Java OutOfMemoryError, a scheduler’s out-of-memory kill and a filesystem error are different problems. First record the exact command, exit status, scheduler memory limit, observed peak resident memory and free space in the temporary directory. A bare “Killed” line does not tell you which allocation failed.

-Xmx limits the JVM heap; it is not the entire process’s memory allowance. Compression, native allocations and other overhead still exist. Increasing heap to the scheduler’s full allocation can therefore leave too little room. Conversely, a job blocked on slow shared scratch will not become fast merely because its heap is bigger.

What you observeWhat to inspect
Java heap errorActual JVM flags, scheduler allowance and sorting-buffer settings.
Scheduler OOM killPeak RSS and cgroup/job limits, not just -Xmx.
Long quiet periodsTemporary-file growth, disk throughput and compression CPU use. Quiet is not necessarily stuck.
No space leftScratch capacity, quota and inode limits. Preserve the failed run for diagnosis.

What Turbo Picard changes.

The native duplicate-marking path removes the Java runtime from this step. It keeps Picard-style arguments and a documented contract for duplicate decisions and metrics. For large eligible inputs it uses a disk-backed two-pass plan rather than retaining every alignment in RAM.

Eligibility matters: a single BAM, a single CRAM with an explicit reference, or already globally coordinate-ordered multiple inputs can use the bounded plan. A collection of separately sorted files is not necessarily globally ordered when processed together. Other multi-input cases can still take an in-memory path.

MAX_RECORDS_IN_RAM controls sorting buffers and TMP_DIR selects temporary storage. Neither is a hard ceiling on total RSS. Large duplicate families, compression buffers and other state still cost memory. Plan scratch space and monitor the actual task.

Try a native run without touching the original.

After an isolated installation, use the explicit Turbo Picard executable. The example below creates its own output directory, preserves optical-duplicate processing and requests a native run only. Use a representative, coordinate-sorted BAM and set the buffer size for your environment; 100,000 below is an example, not a universal optimum.

Shell example
run_dir="$(mktemp -d)"
mkdir "$run_dir/scratch"
TURBO_PICARD_REQUIRE_NATIVE=1 \
  "$HOME/.venvs/turbo-picard/bin/turbo-picard" MarkDuplicates \
  I=/data/sample.bam \
  O="$run_dir/marked.bam" M="$run_dir/duplicate_metrics.txt" \
  TMP_DIR="$run_dir/scratch" MAX_RECORDS_IN_RAM=100000
printf 'Results retained in %s\n' "$run_dir"

For CRAM, add REFERENCE_SEQUENCE=/data/reference.fa using the correct reference and prepare any required reference indexes. Do not assume the filename alone identifies the right assembly.

A faster run is only useful if it remains the right run.

Compare duplicate flags, representative selection, library/read-group handling, barcodes, optical decisions and metrics. Preserve your scoring and filtering options. Setting READ_NAME_REGEX=null disables optical discovery; it changes the task and is not an interchangeable “speed setting.”

The comparison builder creates separate Picard and Turbo outputs and retains the evidence. Add your workflow-specific arguments only after checking the command’s scope. A passing small fixture is a starting point; repeat across the input diversity that matters to your pipeline.

When to keep Picard: an unsupported option, a workflow requiring semantics outside the native scope, or a representative comparison that fails. Native-only mode fails clearly instead of silently turning the trial into a Java run.
