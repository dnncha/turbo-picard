This is a workflow comparison, not a performance ranking. There is no head-to-head production benchmark here establishing that Turbo Picard is faster than all of these tools.

Turbo Picard: keep the surrounding task familiar.

The strongest reason to try Turbo Picard is that your workflow already has a Picard step whose command and output contract you want to retain. Native execution removes Java from the supported path while keeping Picard-style command names and KEY=VALUE arguments.

That reduces the scope of a migration; it does not eliminate validation. Many native commands have scoped support. Check unusual flags, reference requirements, read-group accumulation, duplicate semantics and sidecars. The command catalogue is generated from source so the boundaries are visible before you install.

For unsupported tasks, retaining upstream Picard can be the right answer. Its presence as a fallback is useful compatibility behaviour, but delegated execution must never be counted as native acceleration. Use native-only mode for a performance trial.

A different interface can be the right trade-off.

samtools: compare the prepared workflow.

samtools markdup requires the appropriate sorting and mate information from fixmate -m. If those are not already available, preparation is part of the comparison. If they are already produced upstream, artificially adding them again is unfair too.

Match duplicate definitions, optical handling and downstream requirements. A command name resembling “mark duplicates” is not a guarantee of identical flags, tags or metrics. Similarly, compare FASTQ exports after matching record filtering and ordering.

Riker: native QC with a deliberately different contract.

Riker’s documentation explicitly describes a non-drop-in approach, with different command structure, outputs and intentional behaviour changes. That can be attractive when the pipeline owner is happy to adopt its conventions. It is a different choice from preserving a selected Picard task’s existing interface.

The practical question is not “which project has the best headline?” It is “which tool makes this pipeline better once integration, validation and operation are included?”

Write down the comparison before running it.

Use the same representative inputs and name the scientific fields that must agree. Record tool versions, exact flags, resources, compression, preparation steps and the outputs actually required. Retain failures as well as wins. Measure the whole replaced task; use repeated runs before generalising a timing.

Turbo Picard’s saved fixture suite is useful for inspecting the project’s testing approach. It is not evidence for a whole-genome claim, a comparison with every competitor, or your workflow’s expected saving.
