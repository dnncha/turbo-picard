Workflow validation protocol
============================

This protocol describes the evidence needed before using Turbo-Picard in a
research or clinical pipeline. It separates implemented command behaviour from
validated workflow scope. A passing synthetic benchmark is not sufficient to
approve a workflow change.

Current posture
---------------

Turbo-Picard provides native or partial-native implementations for the
highest-value SAM/BAM/CRAM, metrics, interval, FASTA and VCF paths, with
upstream Picard fallback for the remaining command surface. The saved
suite is useful regression evidence; it is not evidence that every
Picard option or every assay is safe to switch.

Use these statuses in release notes and issue reports:

-  experimental: implementation exists but lacks the relevant real-data
   and option-coverage gates.
-  candidate: command-level parity and benchmark evidence exists for a
   documented scope.
-  production: the documented scope has passed pinned real-data
   evidence, failure-path tests, reproducibility checks and independent
   review.
-  delegated: upstream Picard remains the execution authority.

Release gates
-------------

A command may be called production only when:

1. Its command-matrix entry names the exact native scope, fallback
   scope, comparator and known differences.
2. It passes the synthetic parity suite.
3. It passes a pinned BAM or CRAM real-data bundle with SHA-256,
   immutable source URL or accession, exact versions and machine
   profile.
4. The evidence checks records, headers, indexes, metrics, sidecars,
   exit status and error behaviour consumed by the workflow.
5. Every previously fixed mismatch has a regression fixture.
6. The benchmark records median wall time, p95 wall time, peak RSS,
   temporary disk, input shape, repeat count and parity.
7. Someone other than the implementation author has reviewed the result.
8. python3 tools/verify_real_data_evidence.py --release-ready and python3
   tools/validate_production_manifest.py --release-ready pass.

A workflow is approved for migration only after its owner runs the same
command and option set on representative data. Repository fixtures are
package evidence, not a substitute for workflow evidence.

Golden migration surface
------------------------

Prioritise evidence and compatibility for:

-  MarkDuplicates, including optical duplicates, duplicate-set tags,
   barcode/UMI modes, multiple libraries, supplementary records, CRAM
   and constrained-memory execution.
-  SortSam, MergeSamFiles, FixMateInformation, RevertSam, SamToFastq and
   FastqToSam.
-  AddOrReplaceReadGroups, BuildBamIndex, ValidateSamFile,
   SetNmMdAndUqTags and CreateSequenceDictionary.
-  CollectMultipleMetrics, CollectAlignmentSummaryMetrics,
   CollectInsertSizeMetrics, CollectWgsMetrics, CollectGcBiasMetrics and the
   core ALL_READS path of ``CollectHsMetrics``. The latter now has matching
   Picard fixture parity including per-target/per-base sidecar reports;
   production-sized WES evidence remains open.
-  GatherVcfs, SortVcf, MergeVcfs, LiftoverVcf and
   UpdateVcfSequenceDictionary.

Do not treat small parity fixtures as production-sized evidence, and do not
promote a command beyond its documented native scope without representative
workflow data.

Evidence tiers
--------------

-  smoke: small deterministic fixture for fast regression checks.
-  release_candidate: pinned public data, repeated timings and semantic
   parity.
-  production_scale: workflow- or cohort-sized data with wall time, RSS,
   disk and cost measurements.
-  independent_reproduction: the same evidence regenerated by an
   unrelated person or machine.

Only production_scale plus independent_reproduction supports a broad
performance claim. A smoke fixture must never be the sole basis for a
whole-genome, clinical, cohort or industry-wide claim.

Operational safety
------------------

Keep upstream Picard installed during migration. Start with the explicit
turbo-picard executable. Enable the optional picard shim only inside a
tested environment and only after the exact commands pass comparison.

For a mismatch, stop that command, preserve input hashes and generated
reports, and route the step to upstream Picard through
TURBO_PICARD_FALLBACK_COMMAND. Never silently accept a different
duplicate flag, metric, FASTQ pairing, index, exit status or validation
result.
