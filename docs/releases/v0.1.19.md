# Turbo Picard v0.1.19

This release fixes `CollectWgsMetrics` on real whole-genome data. In 0.1.18 the
command matched Picard on the small parity fixtures and differed on a real
genome. If you ran `CollectWgsMetrics` on whole-genome data with 0.1.18 or
earlier, rerun it with 0.1.19.

## Correctness fix

- On a 4x GRCh38 genome (1000 Genomes HG02675), Picard 3.5.0 reported mean
  coverage 3.815218 over a territory of 3,043,453,562. turbo-picard 0.1.18
  reported 3.600677 over 3,217,346,917.
- `CollectWgsMetrics` now follows Picard's locus pileup. It excludes reference
  `N` bases from the territory, counts supplementary alignments, applies the
  adapter, mapping-quality, duplicate and pairing exclusions in Picard's order
  and counts them per read, and computes theoretical het sensitivity from the
  unfiltered depth and base quality histograms.
- On the whole 4x genome, and on nine option sets on a 139 Mb slice, every
  metric field and every histogram row now equals Picard 3.5.0.
- The parity comparator now requires every WgsMetrics field and histogram row
  to equal Picard's. It previously allowed a territory difference of one and
  overlap differences of 0.05.

Not checked: the 15x and 30x genomes have no Picard output to compare with, and
no CRAM, RNA or long-read input was compared at genome scale. The record covers
one sample on one host. See `benchmarks/wgs-coverage-2026-11-13/README.md`.

## Performance

- `CollectWgsMetrics` on an indexed BAM or CRAM reads the genome as independent
  regions on several threads. `TURBO_PICARD_REGION_WORKERS` sets the worker
  count, and `1` selects the single pass.
- On one host the whole 4x genome took 22 s with six workers and gave the same
  file as Picard 3.5.0, which took 1,034 s.
- The 30x genome took 194 s. `riker wgs` took 147 s on the same input, so
  turbo-picard is slower there: one contig reaches the default
  `LOCUS_ACCUMULATION_CAP` and is reprocessed in a single pass to keep Picard's
  result.

## Options beyond Picard

- `CollectWgsMetrics EXCLUDE_SUPPLEMENTARY=true` counts primary alignments
  only. Picard counts supplementary alignments, so the metrics file starts with
  a comment line that records the setting.

## Known issues

- `tools/verify_gatk_mito_cram_parity.sh` stops at a `ValidateSamFile`
  exit-code difference against Picard 3.5.0. This predates the release and is
  not fixed in it.
- Rust 1.100 clippy flags `needless_range_loop` in `hs_metrics.rs`, so the
  static gate fails on that toolchain. The lint does not change behaviour.
